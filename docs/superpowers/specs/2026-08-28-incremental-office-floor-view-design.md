# 見下ろし型「職場」ビュー設計

## Context

積みゲー消化工場(incrementalゲーム, `/incremental`)は現状、テイアごとの従業員をリスト表示(名前/所持数/コスト/雇うボタン)するのみで、視覚的な手応えが薄いとのフィードバックを受けた。カイロソフト系シミュレーションゲームのような、雇った従業員が見下ろし視点の職場内を動き回る様子を見せる装飾ビューを追加する。

これは3つの独立した改善要望(見下ろし型UI追加/スキルツリーのデザイン刷新/スキルツリー仕様変更)のうち最初の1つ。他の2つは別途スコープする。

## Goals

- 所持している従業員テイアが、見下ろし視点の「職場」パネル内をランダムに歩き回る様子を表示する
- 既存の「積みゲー従業員」リスト(雇用UI)はそのまま維持する。新パネルは装飾専用で、ゲームロジック・状態には一切影響しない
- キャラの見た目は既存の`TIER_THUMB_PALETTE`の色をそのまま流用し、リストの配色と視覚的に一貫させる
- 手描き画像アセットなしで実装できる(CSS/SVGのみで構築するドット絵風キャラ)

## Non-Goals

- スキルツリー画面のデザイン刷新(別スコープ)
- スキルツリーの仕様変更・プレステージ間ロック(別スコープ)
- キャラのクリック操作・インタラクション(将来検討、今回は装飾のみ)
- 経路探索や衝突回避などの本格的な物理・AI(YAGNI、単純なランダムターゲット移動で十分)
- モバイル専用の別レイアウト(既存ページのレスポンシブ方針に乗る)

## Architecture

既存の実装パターンを踏襲する: `web/views/incrementalPage.js` の `CLIENT_SCRIPT`(1つの巨大な文字列として組み立てられ、`<script>`タグにそのまま埋め込まれるIIFE)に、新セクションとして職場ビューのHTML/CSS/JSを追記する。新規ファイルは作らない。

配置順序について: 今回のバグ(`computeOfflineBonusSeconds`がスキルツリー初期化前に呼ばれて例外)の教訓により、**新しく追加するコードが依存する変数(`owned`, `page`, `TIER_THUMB_PALETTE`相当の色配列)がすでに代入済みの位置に挿入すること**を実装時に必ず確認する。具体的には、`tierEls`ループ(所持数を読む処理)より後、かつ`setInterval`のtickループより前に配置する。

### コンポーネント構成

1. **HTML構造**(`renderIncrementalPage`が返すHTML内、従業員リストパネルの直前に追加)
   - `#incremental-office-floor` — 床エリアのコンテナ(固定高さ、`overflow:hidden`)
   - 背景装飾要素(什器/デスクを模した数個の静的div、CSSのみ)

2. **キャラ生成ロジック**(クライアントスクリプト内、新関数 `renderOfficeFloor()`)
   - `owned[]`を見て、所持数>0のテイアごとに1体、テイア順に最大20体までキャラ要素を生成
   - 各キャラは8×8グリッドのドット絵風div(`box-shadow`でピクセルを積む方式。1キャラ=1つのdiv+CSS変数で色指定、DOM要素を極力増やさない)
   - 色は該当テイアの`TIER_THUMB_PALETTE[i % TIER_THUMB_PALETTE.length]`を再利用
   - 呼び出しタイミング: ページ初期化時、および雇用/プレステージ後(所持テイア構成が変わりうる箇所)に再計算

3. **移動ロジック**(新関数、`setInterval`とは別の軽量ループ)
   - キャラごとに `{el, targetX, targetY}` を保持する配列
   - 数百ms間隔(例: 400ms)のタイマーで、床の範囲内のランダム座標をターゲットに設定し、CSSの`transition`(1〜2秒程度)で滑らかに移動させる。到達判定は次のタイマー周期で新ターゲットを都度発行するだけで十分(厳密な到達検知は不要、YAGNI)
   - 職場パネルがDOM上に存在しない場合(要素取得できない場合)は何もしない(既存の`if(!el)return`系のガード規約に合わせる)

4. **既存ゲームロジックとの境界**
   - `owned[]`の読み取りのみ。書き込み・状態変更は一切行わない
   - 既存の`renderTiers()`等のrender関数とは独立した関数として追加し、既存関数の内部には手を入れない

## Data Flow

```
owned[] (雇用/プレステージで更新)
   → renderOfficeFloor() が呼ばれる(雇用ボタンのクリックハンドラ末尾、プレステージハンドラ末尾に追加)
   → 所持テイア構成に応じてキャラ要素をDOMに反映(増減)
   → 独立した移動タイマーが全キャラの位置を継続的に更新(ゲーム状態と無関係に動き続ける)
```

## Error Handling

- 職場パネルのルート要素が見つからない場合は早期returnし、既存の防御的ガード規約(`if(!el)return`)に従う
- キャラ配列の再構築は毎回全消去→再構築のシンプルな方式とし、差分更新の複雑さは持ち込まない(YAGNI、体数上限20なのでコストは無視できる)

## Testing

- 既存の正規表現ベースのテスト(`incrementalPage.test.js`)に、新HTML構造・新関数定義の存在を確認するケースを追加(既存の慣習に合わせる)
- **新規**: 生成された`CLIENT_SCRIPT`をNodeの`vm`モジュール+最小限のDOM/localStorageスタブ上で実際に実行し、例外を投げずに完走することを確認するスモークテストを1本追加する(`incrementalPage.test.js`内、または新規`incrementalPage.smoke.test.js`)。今回の本番クラッシュ(正規表現テストは全通過していたのに実機で例外)の再発防止が目的。DOMスタブは今回のデバッグで使った簡易実装(要素モック+`querySelector`+`localStorage`スタブ)を流用・整備する
