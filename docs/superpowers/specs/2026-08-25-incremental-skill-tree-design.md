# 積みゲー消化工場 スキルツリー設計

## Context

「積みゲー消化工場」インクリメンタルゲーム(`web/views/incrementalPage.js`)に、恒久的な強化を選んで解放していくスキルツリーを追加する。ユーザーからの要望は「未実装のスキルツリーを実装してほしい」、ポイント源については「DPも使うし、プレステージや"レベルアップ"で得られるものも色々混ぜたい」という指定で、詳細はブレインストーミングを通じて以下の通り確定した。

セッション冒頭で検討された「ルーレット用200ノードのスキルツリー」は、ユニークな効果を持つレバーが足りず断念し、代わりに独立した積みゲー消化工場自体を新規作成した経緯がある。今回のスキルツリーはその積みゲー消化工場に対するものであり、ゲーム内に実装済みの多様なレバー(Tier産出・コスト、クリック威力、オフライン上限、ボーナスイベント、プレステージ係数、DP↔コイン交換レート)を根拠に、20ノード規模なら現実的にユニークな効果を割り当てられると判断した。

**「レベルアップで得られるもの」の解釈について**: このゲームにはEXP/レベルシステムが存在しない(ルーレット側`layout.js`には別途EXP/レベルHUDが存在するが、それを参照すると積みゲー消化工場の「他ページの状態を一切見ない」というアイソレーション方針が崩れる)。そのため本設計では、**実績バッジの解禁をこのゲームにおける"レベルアップ"の代替イベント**として扱い、SP獲得源の一つとする。ユーザーはこの解釈で承認済み。

## 決定事項

- **スキルポイント(SP)は独立した新規資源**とし、DPやプレステージ倍率とは別に管理する。
- ツリーは**プレステージ(新年度リセット)しても保持される**恒久要素。SP残高・解放済みノードは`dp`/`owned`のようにリセットされない。
- ノード規模は**約20ノード**、3ブランチ構成。
- 各ブランチは**直線チェーン**(前のノードを解放しないと次に進めない)。分岐グラフにはしない(規模に対して複雑すぎるため)。
- **ノード定義はNode(サーバー)側モジュールスコープに1箇所だけ**定義し、`JSON.stringify`でクライアントスクリプトへ渡す。現状`DP_TO_CREDITS_RATE`等がモジュール側とクライアント側の2箇所に別々にハードコードされている構造上のリスク(将来どちらかだけ変更されて表示と実際の値がズレる)を、今回は繰り返さない。
- 派生倍率の計算関数は**純粋関数としてexportし、regexアサーションだけでなく実際の計算結果を検証するテスト**を書く(既存の`incrementalPage.test.js`はレンダリング済みHTML文字列へのregexマッチのみで、実際のJS実行結果を検証していない)。
- 為替レート改善ノードは**レート(必要DP量)だけを改善**し、`DP_TO_CREDITS_DAILY_CAP`(1日300枚のインフレ防止上限)自体は変更しない。上限はクレジット単位で固定されているため、レート改善によって1日に生成可能なクレジット総量が増えることはない。

## SPの入手源

1. **プレステージ時**: `spGain = Math.max(1, Math.floor(Math.sqrt(lifetimeDp / 500000)))` を毎回獲得(常に最低1、既存の`prestigeMult`計算と並行して加算)。
2. **実績解禁時**: 5段階の実績バッジ(既存`MILESTONES`)を新規解禁するたびに `(解禁順位)` SPを獲得(1個目→1SP、2個目→2SP…5個目→5SP、合計15SP)。既存の`lastAchievedCount`による新規解禁検知ロジックをそのまま流用する。
3. **DP研究投資**: 新規ボタン「🔬 研究にDPを投資」。1回につきSP+1を獲得し、DPを消費する。コストは使用回数に応じて`RESEARCH_BASE_COST * Math.pow(RESEARCH_COST_GROWTH, useCount)`で増加(`RESEARCH_BASE_COST=500`, `RESEARCH_COST_GROWTH=1.25`)。使用回数は新規永続キーに保存し、連打による無限SP稼ぎを防ぐ。

## データモデル

- `ja_trans_incremental_sp_v1`: SP残高(数値、文字列化して保存)。
- `ja_trans_incremental_skills_v1`: `{production:N, management:N, luck:N}` (各ブランチの解放済みノード数、0〜ブランチ長)。
- `ja_trans_incremental_research_uses_v1`: 研究投資ボタンの使用回数(数値)。

いずれもプレステージの`RESET_KEYS`相当のリセット対象には含めない(恒久要素のため)。

## 効果の適用箇所

- `totalOutputPerSec()`: `sum * prestigeMult * skillOutputMult()` に変更。
- `tierCost(i, ownedCount)`: `tierBaseCost(i) * Math.pow(TIER_COST_GROWTH, ownedCount) * skillCostMult()` に変更。
- クリックハンドラ: `addDp(CLICK_BASE * prestigeMult * skillClickMult())`。
- オフライン計算: `offlineGain = totalOutputPerSec() * elapsedSec * (skillHasOfflineBoost() ? 1.5 : 1)`。
- `EXCHANGE_RATE` / `DP_TO_CREDITS_RATE`: 実効値を`effectiveExchangeRate()` / `effectiveDpToCreditsRate()`のような派生関数経由で参照するよう変更(`DP_TO_CREDITS_DAILY_CAP`はそのまま)。
- `scheduleBonus()`の間隔、ボーナス獲得量計算: それぞれ`skillBonusIntervalMult()` / `skillBonusValueMult()`を乗算。
- プレステージ計算: `prestigeMult = 1 + PRESTIGE_COEF * skillPrestigeCoefMult() * Math.sqrt(lifetimeDp / PRESTIGE_DIVISOR)`。
- 固有効果(自動発注・秘書雇用・幸運の従業員自動回収)は、対応するブランチの最終ノードが解放済みかどうかを見るブール関数(`skillHasAutoBuy()`など)で判定し、既存の`setInterval`ティックや`spawnBonus()`にフックする。

## UI

新セクション「🌳 スキルツリー」を積みゲー消化工場ページに追加する。既存のカイロソフト風デザイン言語(太い黒縁取り・丸パネル・パステル配色)を踏襲する。

- SP残高表示チップ(既存HUDと同様の見た目)。
- 「🔬 研究にDPを投資」ボタン(次回コストを表示)。
- 3ブランチを横に並べた列。各列はノードを縦の「ビーズ」(丸)で連結線とともに表示し、解放済み/解放可能/未解放(前提未達 or SP不足)を色分けする。クリックで解放を試みる。

## テスト方針

既存の`incrementalPage.test.js`の regex アサーション形式に加え、以下を新規に追加する:

- ノード定義配列(`SKILL_BRANCHES`)をモジュールから`export`し、直接importして「コストが各ブランチ内で単調増加していること」「各ブランチの最終要素が`kind:"unique"`であること」を検証。
- 派生倍率の純粋関数(`computeOutputMult(skillLevels)`など、DOM非依存の形でexportする)を直接呼び出し、「全ノード解放時に期待通りの倍率になる」ことを計算で検証。
- 引き続き`new Function()`によるクライアントスクリプトの構文検証テストを維持する。

## スコープ外

- 分岐する真のグラフ構造(前提条件が複数ノードにまたがるもの)。
- ルーレット側EXP/レベルシステムとの連携。
- 見下ろし視点のキャラクターアニメーション等(別タスクとしてユーザーが明示的に後回しにした)。
- スキルツリーのリセット/やり直し機能(一度解放したノードは永続、v1では未実装)。
